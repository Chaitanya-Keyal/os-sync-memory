PART A - transitive priority inversion
--------------------------------------

Scenario (all SCHED_FIFO on CPU 0; busy work = thread CPU time, so a
preempted thread makes no progress):
  L prio 10, t=0     lock M1, 600 ms work, unlock M1
  D prio 20, t=100   lock M2, lock M1, 100 ms work, unlock M1, unlock M2
  H prio 30, t=200   lock M2 (then unlock it)
  X prio 25, t=300   2000 ms work, no mutex
H blocking time  = time from calling lock(M2) to acquiring it
H response time  = time from H's intended release (200 ms) to acquiring M2

Predictions (written before running)

PRIO_NONE. L runs 0-100. D preempts, takes M2, blocks on M1. L runs 100-200.
H preempts, blocks on M2 (held by D). L runs 200-300 (300 ms of work done).
X (25) preempts L (10) and runs 300-2300. L finishes its last 300 ms at
2600 and unlocks M1. D runs 2600-2700 and unlocks M2. H gets M2 at 2700.
  blocking = 2700 - 200 = 2500 ms, response = 2500 ms
  (the CPU is never idle from 0 to 2700 ms: L 600 + X 2000 + D 100).

PRIO_INHERIT. At 100 D blocks on M1 and L inherits 20. At 200 H blocks on M2:
D inherits 30, and because D is itself blocked on M1 held by L, the boost is
passed along the chain, so L also runs at 30. X (25) cannot preempt L. L
finishes at 600, D (still at 30) runs 600-700, H gets M2 at 700. X runs
700-2700.
  blocking = 500 ms, response = 500 ms

PRIO_PROTECT (ceiling 30). Locking M1 at 0 raises L to 30 immediately. At
100 D (20) cannot preempt; at 200 H (30) is equal, not higher, so under FIFO
it waits behind L; X (25) cannot preempt either. L finishes and unlocks M1
at 600 and drops back to 10. H, the highest ready thread, now runs for the
first time, calls lock(M2) - and M2 is free, because D never got to run and
lock it. X runs 600-2600, then D 2600-2700.
  blocking = 0 ms, response = 600 - 200 = 400 ms

Mismatch. Every measured value is within 1.2 ms of the prediction. The
small excess is overhead: each run starts with the releaser waking threads
over an inter-processor interrupt (about 0.1-0.5 ms), context switches,
the futex system calls on each lock/unlock (PI mutexes always go through
the kernel), and for PRIO_PROTECT glibc's sched_setparam calls on lock and
unlock (L's lock M1 took 0.6 ms in run 1).

Why blocking and response differ for PRIO_PROTECT. Blocking time only starts
when H calls pthread_mutex_lock. With a ceiling of 30, L runs at priority 30
from the moment it locks M1, so H (also 30) cannot even start until L
unlocks at 600 ms. H's whole 400 ms delay is spent *before* it calls lock,
waiting for the CPU, and its lock call then succeeds at once. The ceiling
turned "blocked on a mutex" into "not yet scheduled": blocking time is ~0,
but the response latency (400 ms) shows the real delay. In the other two
versions H runs at once at 200 ms and all the delay is inside lock(), so the
two numbers are equal.

How the threads are released. A thread that sleeps with clock_nanosleep
needs a timer interrupt to wake up. On our VirtualBox VM (which runs on
Hyper-V because WSL2 is enabled on the host) timer interrupts reach a busy
vCPU 10-200 ms late: a test that slept 10 ms a hundred times was on average
24 ms late and once 245 ms late, and D sometimes started after H, which
breaks the chain. So by default prio_chain starts a "releaser" thread on
CPU 1 (prio 99) that spins on CLOCK_MONOTONIC and wakes each thread at its
start time through a condition variable. That wakeup arrives as an
inter-processor interrupt, measured at 0.2-1 ms late. The four test threads
still all run on CPU 0, so the inversion itself is unchanged. `./prio_chain
-t` uses clock_nanosleep on CPU 0 instead (fine on bare metal).

Cross-check with plain timers on a 1-CPU machine. The late timers only
happen with 4 vCPUs: with the VM set to 1 vCPU, timer wakeups were 0.3 ms
late on average. There we ran `sudo ./prio_chain -t 5` (every thread
sleeps with clock_nanosleep, no second CPU at all). Output:
run_output_1cpu_timers.txt.

  version        blocking (pred / meas)   response (pred / meas)
  PRIO_NONE        2500 / 2521.80           2500 / 2529.42
  PRIO_INHERIT      500 /  494.00            500 /  501.63
  PRIO_PROTECT        0 /    0.05            400 /  400.67

Same results, a little noisier, for two reasons. The releases are now a
few ms late (D started at 105.6 ms in run 1); a late H makes its blocking
time shorter by that amount (INHERIT 494 ms). And with a single CPU, normal
tasks (sshd, kernel workers) can only run on that CPU: the kernel's fair
server reserves them up to 50 ms per second even over SCHED_FIFO threads,
which adds roughly 20-30 ms to the 2.7 s PRIO_NONE run.

Short note
----------
Priority inheritance only helps when a high-priority thread waits for a
lower-priority one that is able to run: it lends priority so the holder
finishes sooner. In Part B every thread is blocked on a lock held by another
blocked thread, so there is nobody to boost; raising priorities cannot break
a cycle. The fix breaks the Coffman condition "no preemption" (and with it
hold-and-wait): a thread that times out gives back the lock it holds, so the
circular wait cannot last. It can still livelock in theory: if all three
time out together, back off for the same time and retry in lockstep, the
cycle forms again forever. The random 50-250 ms backoff (independent seed per
thread and run) makes repeated identical timing very unlikely, and in 20 runs
no thread ever needed more than one retry.
